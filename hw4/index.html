Overview (3 pts)

In this assignment I built a real-time cloth sim using a mass-spring model. I started by generating the grid of point masses and springs, then added forces + Verlet integration with damping and a Provot-style stretch limit for stability. After that I implemented collisions with spheres/planes and self-collisions using spatial hashing so the cloth doesn’t clip through itself. Finally, I wrote a set of GLSL shaders (diffuse, Blinn-Phong, texture mapping, bump/displacement, and environment-mapped mirror) to render the cloth with more realistic lighting and materials. The coolest part for me was seeing how small parameter changes (like \(k_s\), density, damping) and mesh resolution can totally change the look and behavior.

Part 2: Simulation via numerical integration (20 pts)

Effects of spring constant \(k_s\)

When I lowered \(k_s\) a lot, the cloth basically acted like a loose, stretchy fabric: it deformed a ton under gravity and the pinned corners could “pull” a long way before the springs noticeably fought back. It also tended to look kind of drapey and you could see bigger, smoother sagging shapes.

When I cranked \(k_s\) up really high, the cloth felt much stiffer. It didn’t stretch much, and instead of sagging deeply it kept a tighter shape and made sharper folds / wrinkles. Compared to the default, high \(k_s\) looked more “rigid sheet”, while low \(k_s\) looked more “rubber cloth.”

Effects of density

Changing density mostly changed how “heavy” the cloth felt. With higher density, gravity had more effect, so the cloth would sag more aggressively and it tended to hit a deeper resting shape. With lower density, it felt lighter and didn’t droop as much, and the motion looked a bit more floaty.

Compared to the default parameters, the most obvious difference for me was how deep the cloth sagged and how strong the folds got when it was heavier versus lighter.

Effects of damping

Damping mainly controlled how quickly the cloth stopped wobbling. With low damping, it kept oscillating for a while and you could see it “ring” after the initial drop. With higher damping, the motion died out much faster and the cloth reached a stable resting state without as much bouncing.

If damping is set really high, the motion starts to look kind of dead/overdamped (like it’s moving through thick syrup), which makes it settle quickly but also looks less realistic.

Part 3: Handling collisions with other objects (20 pts)

Collision handling implementation (spheres and planes)

For collisions, I treated each point mass like a particle that can’t end up “inside” the collision primitive after a timestep. Each frame, after I do Verlet integration, I loop over all point masses and call collide() on every collision object in the scene.

Sphere: I check if the point mass ended up inside the sphere by comparing the distance to the sphere’s center against the radius. If it’s inside, I compute the tangent point on the sphere surface in the direction from the center to the point. Then I compute a correction vector from last_position to that tangent point, and set the new position to last_position plus that correction, scaled down by \((1 - f)^2\) so higher friction makes the point “stick” more instead of sliding freely.

Plane: For the plane, I check if the point mass crossed from one side of the plane to the other between last_position and position (sign change of the dot product with the plane normal). If it crossed, I solve for the intersection point (tangent point) along the straight segment from last \(\rightarrow\) current, then push the point slightly off the plane by a tiny SURFACE_OFFSET on the original side. Like the sphere, I apply friction by scaling the correction by \((1 - f)^2\).

Sphere collision results (sphere.json) with varying \(k_s\)

With a low \(k_s\) (like 500), the cloth is much stretchier and it tends to droop more over the sphere, with smoother, larger-scale folds because the springs don’t resist deformation much. At the default \(k_s = 5000\), it still drapes nicely but it holds its shape better and the folds look more “fabric-like.” With a very high \(k_s\) (like 50000), it barely stretches and looks noticeably stiffer, so the cloth sits more like a rigid sheet draped over the sphere with tighter / sharper wrinkles.

Part 4: Handling self-collisions (20 pts)

Self-collision implementation

The main problem with self-collision is that checking every pair of point masses is \(O(n^2)\), which is way too slow once the cloth grid gets bigger. To make it fast enough, I used spatial hashing.

Every timestep, I split space into 3D boxes with size \(w = 3 \cdot \frac{\text{width}}{\text{num\_width\_points}}\), \(h = 3 \cdot \frac{\text{height}}{\text{num\_height\_points}}\), and \(t = \max(w, h)\). For each point mass, I “snap” its position into one of these boxes by truncating the coordinates to the nearest box corner (basically flooring to a grid). I then hash that snapped \((x,y,z)\) into a key and insert a pointer to the point mass into a hash map from key \(\rightarrow\) list of point masses in that same box.

To resolve self-collisions for a given point mass, I only compare it against the other point masses in its own hashed box. If another point mass is closer than \(2 \cdot \text{thickness}\), I compute a correction that would separate them to exactly that distance (along the direction between them). I average all the corrections for that point mass and then divide by simulation_steps so the correction doesn’t happen too suddenly in one substep.

Part 5: Shaders (20 pts)

What is a shader program? Vertex vs fragment shaders

A shader program is basically a little program that runs on the GPU as part of the graphics pipeline. Instead of doing all the math on the CPU for every pixel, the GPU runs the shader in parallel across tons of vertices/fragments at once, which is why it can hit real-time framerates.

The vertex shader runs once per vertex. In our case it takes in the mesh attributes (position, normal, tangent, UV) and applies the model and view-projection transforms. It also outputs “varyings” like the world-space position/normal/UV, which then get interpolated across each triangle during rasterization.

The fragment shader runs once per fragment (basically per pixel sample). It reads the interpolated varyings and does the actual shading math (lighting, texture lookups, etc.), and outputs the final RGBA color. The two shaders work together because the fragment shader is using the data the vertex shader prepared + the rasterizer interpolated.

Blinn-Phong shading model

Blinn-Phong is a simple lighting model that adds up three pieces: ambient + diffuse + specular. The ambient term is just a constant base light so the object isn’t completely black when it’s not directly lit. The diffuse term is Lambertian shading, so it depends on \(\max(0, n \cdot l)\) — basically how much the surface faces the light. The specular term creates the shiny highlight.

The “Blinn” part is that instead of reflecting the light vector, you compute the half-vector \(h = \frac{l + v}{\|l + v\|}\), where \(l\) is the light direction and \(v\) is the view direction. Then you use \(\max(0, n \cdot h)^p\) to control the sharpness of the highlight with exponent \(p\).

Bump mapping vs displacement mapping

Bump mapping and displacement mapping both use a height map texture, but they change different things. Bump mapping only changes the normal used for lighting, so the silhouette/outline of the object doesn’t actually change — it just looks bumpy because the lighting reacts like the surface is tilted. Displacement mapping actually moves the vertices along the normal based on the height map, so the geometry changes for real and you can see it in the shape (especially along edges and in strong lighting).

On the sphere, mesh resolution matters a lot more for displacement than bump. With a coarse sphere mesh (\(-o 16 -a 16\)), displacement can look blocky or “low poly” because you’re literally moving a small number of big triangles. With a fine mesh (\(-o 128 -a 128\)), there are way more vertices to displace, so the shape looks much smoother and the height map detail comes through better. Bump mapping is less sensitive to mesh resolution since it doesn’t move vertices, but you can still see differences because the interpolated normals change across larger triangles.
